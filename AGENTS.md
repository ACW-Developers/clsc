# Architecture rules

- Stay a React + Vite + TypeScript SPA with react-router-dom; no framework migration — explicit owner requirement.
- Route paths live only in `src/routes/paths.ts`; routes are declared in `src/routes/AppRoutes.tsx` under `RootLayout` — one place to change URLs.
- Pages (`src/pages`, `*Page.tsx`) compose components; layouts in `src/layouts`; shared app components in `src/components/common`; shadcn primitives in `src/components/ui` untouched — clear ownership.
- Backend access only via `src/services/*` consumed through React Query hooks in `src/hooks` — keeps data access in one pattern and testable.
- Client env vars are read only through `src/config/env.ts` (zod-validated); private keys never go in client code — security.
- Global providers live in `src/providers/AppProviders.tsx` — single composition point.
- Future modules (hospitality, bookshop, programmes) get their own subfolders inside pages/components/services/hooks — modular growth.
- Orders and donations use module-specific services/hooks and a shared records view; customers read their own records, staff manage fulfilment and notes, and payment state remains server-owned — keep trusted transaction state separate from administration.
- Bookshop catalogue and stock use module-specific services/hooks; atomic checkout locks branch stock, snapshots order items and issues separate bookshop receipts while reusing the orders table — prevent overselling and preserve hospitality receipts.
- Bookshop cart stores only branch, book IDs and quantities locally; checkout derives prices and ownership on the server — browser state must never authorize payment or set prices.
- RootLayout owns navigation scroll reset for path/query changes, preserving deliberate section anchors — consistent navigation across all pages and dashboard views.
- Use semantic design tokens from `src/index.css`; no hardcoded color utilities — theming consistency.
- Load the site-wide font locally in AppProviders and map all Tailwind font families to it — consistent typography across headings, legacy utilities and receipts without external font requests.
- Keep hospitality administration behind one role-guarded `/admin` page with query-driven views, reusing the existing service and React Query layers so staff permissions stay centralized.
- First super-admin setup is two-step (register approved mailbox, then claim after email confirmation) in the setup-admin function — server enforces approval and one-time use.
- Keep first-admin eligibility in the setup function's shared policy module with focused tests — registration and claiming must enforce the same approval.
- Unbuilt modules route to a shared Coming Soon page driven by `src/config/navigation.ts` — one place to grow the menu.
- All checkout (Paystack or M-Pesa Daraja STK Push) starts and verifies through the paystack edge function; M-Pesa success is only accepted after a Daraja status query, callbacks are matched by a per-session token; only service-role finalization can call the legacy payment RPCs, with atomic idempotence and test-domain/amount/currency checks — clients cannot forge paid state. Payment status changes ring a data-free broadcast doorbell on `pay-<reference>` (polling is the fallback), identical pending M-Pesa checkouts are reused instead of re-prompting, and callback failures may only cancel a pending session.
- Paystack callback origins use an explicit allowlist in the payment policy; add the published/custom origin only when approved — prevent checkout redirect abuse.
- Category display and form fields share src/config/facilityCategories.ts; facility information is stored in sub_services.details and booking requests in notes — consistent rendering without changing trusted pricing rules.
- Dashboard charts use the existing Recharts dependency and theme controls use next-themes in AppProviders — reuse dependencies and semantic tokens.
- Admin traffic, overview and log charts share presentation tokens and local-calendar daily aggregation; unavailable traffic dimensions remain explicit instead of changing privacy-conscious tracking for a visual reference.
- Traffic tracking uses a validated rate-limited public RPC with staff-only reads; collect only sanitized page paths and browser-reported device/OS, never query strings, form values, IPs or user identity — keep analytics minimal and privacy-conscious.
- Shared StatCard and profile/security forms serve dashboard modules; signup consent is validated through the shared registration schema — maintain consistent presentation and submission rules.
- Facility uploads are resized and compressed before storage; labelled sample media uses asset pointers — reduce transfer size without changing logo storage.
- Student programmes (events, materials, donations, devotionals, Bible study, student contributions) live in `services/programmes`, `hooks/programmes`, `components/programmes` and `pages/programmes`; ticket and donation payments run only through security-definer RPCs that set prices, capacity and receipt numbers — clients never write payment records.
- All receipts and tickets render through `components/common/PosReceipt` — one universal receipt format across modules.
- Student contributions are moderated by super admins; approval publishes to devotionals/Bible study only via a database trigger with author attribution — clients never publish their own submissions.
- Leadership team records live in `public.leadership_team`, managed via `services/leadership.ts` + `hooks/useLeadership.ts` and the super-admin Leadership view; the About page renders only published members — keep team content server-driven, never hardcoded.
- Reviews live in `public.reviews`; eligibility (paid book order or paid, started facility booking) and author name are enforced by the `guard_review` trigger, super admins moderate via the Reviews view — clients cannot self-certify purchases.
- Live chat visitors are anonymous and hold a secret session token in localStorage; they only use token-checked RPCs and get a data-free broadcast doorbell on `chat-<token>`, while staff read tables via RLS — no table access for anon.
- Programme areas are fixed in `config/programmeAreas.ts` (slugs = `programme_activities.area` check); activities are super-admin managed, shown published-only.
